背景

一期已经定义了"点击推送跳转到目标页"和"前台展示引导授权文案"这两项能力，但正式接入后走查发现前台并未真正生效——用户点击通知后无法跳转到目标页，授权提示展示的也不是后台配置的文案。二期先把这两项能力补齐上线（第1、2条），再新增"同一用户多端（Web/App）各自独立路由"的规则，覆盖一期没有定义过的多端场景（第3条）。

本次二期做的 3 件事

1）跳转链接生效：后台把跳转目标配置好之后，前台用户点击收到的推送通知，能正确跳转到对应页面。详见「消息推送」模块。

2）引导授权文案生效：后台"推送配置"里配置的引导授权文案（默认或自定义），前台弹出授权提示时必须真实展示这段文案。详见「推送配置」模块。

3）多端推送路由：用户在哪个已安装的客户端（Web 或 App）收到推送，点击后就在这个客户端自己的路由里跳转。详见「多端推送与频控」模块。

整体业务流程（三个模块串起来看）

上面 3 件事对应的 Tab 顺序，是按本次需求被发现/讨论的先后排的，不代表真实发生的时间顺序，容易造成误解，这里单独说明：引导授权（「推送配置」模块）是用户安装并打开应用后就要完成的一次性系统权限设置，和"有没有发过某一条具体的推送消息"完全无关——不是"先发了一条推送、用户才被要求授权"，而是"必须先有用户已经授权，运营配置并发送的任意一条推送（「消息推送」模块）才谈得上能不能送达、点击后跳不跳得过去"。多端各自独立收发的规则（「多端推送与频控」模块）建立在前两者之上。

前台展示与交互

用户完成安装（App 安装包，或 PWA 添加到主屏幕）并打开该应用后，会先弹出一个站内软性提示条，引导用户开启通知；提示条里的文案必须真实读取并展示后台"引导授权文案"配置（不管选的是默认还是自定义），不能用写死的文案。用户点击"接收通知"类按钮后，才会继续弹出系统级授权提示。此流程只对"已安装"用户生效，纯网页访问（浏览器标签页直接打开、未安装）不会触发这个流程。用户完成授权后，才能正常接收后续推送。

已安装（App 或 PWA 添加至主屏幕），打开该应用弹出站内引导提示条，文案取自「引导授权文案」配置（默认或自定义）

系统授权提示用户点击拒绝收不到推送，效果同拒绝引导提示条

后台配置

「消息推送」发送时可勾选 Web、App 一端或两端下发，本模块无新增配置项。推送发送的节奏（即"频控"）由运营在「消息推送」页面通过已有的"定时推送"配置（全部 / 仅一次 / 每天）自行把控，这是一期已有的能力，本期未做任何改动，不涉及新增的系统级频率限制。为方便对照，"定时推送"三种模式的触发条件与效果如下（均为一期已有能力，非本期新增）：

定时推送模式触发条件效果
关闭定时推送点击"推送"按钮立即向所有满足勾选条件（Web/App）的用户发送一次
仅一次到达配置的指定时间点在该时间点自动发送一次
每天每天到达配置的时间点按设定时间每天重复发送一次，直到任务被停止/删除

前台展示与交互

用户在哪个已安装的客户端（Web/PWA 或 App）收到推送，点击后就在该客户端自身的路由体系里跳转，不做跨端统一处理。若同一用户 Web、App 都登录且都被运营勾选，两端会各自独立收到一条推送，不做去重或合并——这是本期确认的预期行为。

本条推送勾选了 Web→Web 端收到推送，点击后在 Web 自身路由跳转
本条推送勾选了 App→App 端收到推送，点击后在 App 自身路由跳转
图：多端推送路由规则
触发条件系统反馈
消息推送仅勾选 Web只有 Web 端收到推送，App 不收到
消息推送仅勾选 App只有 App 端收到推送，Web 不收到
消息推送勾选 Web+App，且用户在两端都已登录两端各自独立收到一条推送，不做去重或合并
消息推送勾选 Web+App，但用户从未在其中一端登录/使用过（该端从未与账号的推送别名绑定）基于极光按别名（通常对应用户账号）下发推送的机制，从未绑定该账号别名的那一端收不到；同一账号在多台设备间重复登录时是否要解绑旧设备的别名，是另一个尚待拍板的独立问题，不在本表讨论范围内
